# Phase 4E-10 Text Box / DrawingML / VML Representation Audit

## Scope

This is an audit-first phase. No production source code was changed.

## Parser Behavior

`parseParagraphs` collects all descendant `w:p` elements under `w:body`.
`parseRuns` collects all descendant `w:r` elements under each paragraph, excluding
only deleted tracked-change runs through the Phase 4E-9A `w:del` ancestor policy.

Because `w:txbxContent` also contains `w:p/w:r/w:t`, VML textbox content is
currently reconstructed twice:

1. as descendant runs of the outer carrier paragraph
2. as a separate inner textbox paragraph

The normalized `Paragraph` model has no textbox-specific metadata, so body scope
helpers treat these paragraphs as ordinary body paragraphs unless another
existing exclusion happens to apply.

DrawingML / WordprocessingShape text boxes also represent text through nested
textbox content (`w:txbxContent` or equivalent text-body structures). The current
namespace-descendant traversal has no shape/textbox boundary model, so the same
architectural risk applies. This audit fixture uses deterministic VML OOXML.

## Root Cause

OOXML nested textbox paragraphs
-> `getBodyDescendants(xmlDocument, "p")` includes textbox inner `w:p`
-> outer paragraph `parseRuns` also sees textbox descendant `w:r`
-> normalized document contains duplicated textbox text
-> body scope and section detection have no textbox metadata
-> typography and section validators evaluate textbox text as ordinary body text

## Phase 4E-10A Design Notes

Recommended minimum production-safe direction:

1. Stop outer paragraph run traversal from absorbing runs whose nearest paragraph
   owner is inside `w:txbxContent`.
2. Model textbox paragraphs as a separate content scope instead of ordinary body
   paragraphs.
3. Decide rule-by-rule whether textbox visible text should be included. For
   example, academic body typography and section order likely should not treat
   decorative shape text as normal thesis body paragraphs.
4. Avoid blindly dropping all textbox text forever; it is visible to the user and
   may later need explicit validation.

Do not implement this design in Phase 4E-10.
